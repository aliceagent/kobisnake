# `tests/sim/replays`

Recorded whole-round fixtures (`docs/sprints/sprint-02-core-simulation.md` KS-02-06, `QA-STRATEGY §3`).
`tests/sim/replay.test.js` loads every `*.json` file in this directory except `replay.schema.json` itself,
replays it through `runRound` (`tests/sim/harness.js`), and asserts the resulting event log equals the file's
`expectedEvents` exactly. `replay.schema.json` documents the shape a fixture must have; there is no schema
validator wired in (adding one is a dependency, which needs Opus's approval per `CLAUDE.md`), so `replay.test.js`
checks the handful of required fields itself.

## Why a recording, not a live re-run

`QA-STRATEGY §3`: "Replays: `tests/sim/replays/*.json` store `{seed, settings, inputs, expectedEvents}` recorded
from real sessions that exposed bugs. Every fixed bug adds a replay." A replay is a regression test with the
input log baked in — it must keep failing (or keep passing) the same way forever, independent of which bots
exist or how they play today.

## The tick, not the wall-clock time

Each entry in `inputs` is `{ t, player, dir }` — the ticket's own field names — where `t` is simulated seconds
since round start, exactly like an event's own `t`. But `t` is **resolved to a tick** with
`Math.round(t * settings.simHz)` before it is ever applied, and delivered on that exact tick, never at a
wall-clock instant.

This matters because `RoundSimulation.advance(dt)` only checks for a due input at whatever `dt` chunks the
caller happens to drive it with (`src/core/round.js`). An input recorded as "at t = 0.31 s" can land on tick 37
under one `dt` and tick 38 under another — `tests/sim/determinism.test.js`'s
`AC3: a coarser frame moves when an input lands, not how the round runs` test demonstrates exactly this and is
why replays exist as tick-exact recordings rather than time-exact ones: resolving `t` to a tick once, up front,
and applying it exactly there (`harness.js`'s `driveWithInputLog`) is what makes a replay reproduce the same
round no matter what `dt` a future engine change happens to drive it with.

## `dir` is a name, not a vector

`dir` is one of the strings `UP | DOWN | LEFT | RIGHT` rather than a raw `{dx, dy}` pair, because a replay file
is meant to be read and hand-edited by a QA engineer recording a bug, not only generated by code
(`replay.schema.json`). `harness.js` maps the name to a `src/core/grid.js` `DIRECTIONS` vector before calling
`RoundSimulation.applyInput`.

## `no-input-round.json`

The one fixture this ticket requires (AC3): seed `1`, two players, **no inputs at all**. Both snakes drive
straight into the outer wall on the same tick and the round is a `DRAW` — the golden case `RoundSimulation`
ships with its own copy of, generated by the merged KS-02-05 code and committed at
`tests/unit/core/__golden__/no-input-round.json`. This file's `expectedEvents` is that same event log, and
`replay.test.js` cross-checks the two are byte-for-byte identical as well as running this file through
`runRound`. If the two ever disagree, one of them is wrong — the fix is never to edit either file to match the
other without first working out which one is describing a bug.

## Adding a replay

1. Reproduce the bug with a seed and an input log (a bot's decisions work too — record what `runRound` actually
   applied, not what you intended to send).
2. Fix the bug.
3. Save `{ seed, settingsOverrides, inputs, expectedEvents }` as a new `*.json` file here, with `expectedEvents`
   set to the *fixed* engine's output for that seed and input log.
4. `replay.test.js` picks it up automatically — no code change needed there.
