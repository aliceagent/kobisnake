# Mutation, once — `src/game`

KI-17-04 (`docs/sprints/improvement-17-mutation-testing.md`). One run over `src/game`, for information —
unlike `docs/qa/playtests/mutation-baseline.md`, **nothing here gates anything today.** The table and
survivor list were generated by `node scripts/mutation-report.mjs` from this run's own JSON report; everything
above and below the generated part is this document's own.

Scope: `src/game/**/*.js`, judged by `tests/unit/game/**/*.test.js` and `tests/agent/**/*.test.js` (not the
project's own `npm run test:mutation` — that command runs `stryker.config.mjs` against `src/core`, and is
untouched by this ticket). "Which tests judged it, and why" below says what was tried, what was dropped, and
why. This run's command, in full:

```
npx stryker run <throwaway stryker config> --mutate 'src/game/**/*.js'
```

The throwaway config overrides `mutate` and `vitest.configFile` from the project's own `stryker.config.mjs` /
`vitest.mutation.config.js` and is not committed — see "Which tests judged it, and why".

**Mutation score: 72.22 %** — 1581 of 2189 mutants detected, 608 undetected.

**That is a worse number than `src/core`'s 85.61 % baseline, and it should be read as one, not explained
away.** Some of the gap is a real difference in how thoroughly `src/game` is unit-tested (see "Ten worst
survivors" and the per-file table below); some of it is an artefact of what this run could afford to judge
with — `src/game/bots/levels.js` in particular is not nearly as untested as its 23.08 % makes it look, because
the one suite that actually drives it (`tests/sim/cpuLevels.test.js`, backing the committed
`docs/qa/playtests/cpu-levels.md`) could not be included. Both things are true at once, and the per-file notes
below say which is which rather than picking the flattering reading.

## Which tests judged it, and why

`stryker.config.mjs` and `vitest.mutation.config.js` are untouched — both are KI-17-01/KI-17-03's, scoped to
the `src/core` gate. This run used two throwaway config files, outside the repo (a scratch directory, not
committed), overriding only `mutate` and `vitest.configFile`:

- **`tests/unit/game/**/*.test.js`** — the obvious core of it, and a close line-count match for `src/game`
  itself (5600 source lines against 6285 test lines, file for file). Every one of `src/game`'s 13 files has a
  dedicated suite here.
- **`tests/agent/**/*.test.js`** — already part of `npm run test:unit`, and the `.test.js` half of
  `tests/agent` (never `.spec.js`, which is Playwright and was never going to run under Stryker's Vitest
  runner). `invariants.test.js` imports `session.js` directly.
- **`tests/sim/**/*.test.js` was tried and dropped.** It is the obvious second candidate — `cpuLevels.test.js`
  and `matchTermination.test.js` import `src/game/bots/levels.js`, `bots/policy.js` and `session.js` directly,
  and `tests/sim/bots/{greedyBot,survivorBot}.js` wrap `bots/greedy.js` / `bots/survivor.js` for the fuzz and
  stats suites — this is where `src/game`'s bots are actually driven through full simulated matches, the same
  role `tests/sim` plays for `src/core`. Including it failed outright, not just slowly: the dry run's
  `tests/sim/cpuLevels.test.js` hook exceeded even a 90-second timeout once every mutable statement in
  `src/game` carried Stryker's per-test coverage instrumentation, on a container also running a sibling
  agent's `src/core` mutation run and a CI job at the same time. Raising the timeout further would only have
  deferred the same cost from the (once-only) dry run to every mutant `tests/sim` covers — hundreds of them —
  which is the exact multiplication `stryker.config.mjs`'s own header already declined to pay for `src/core`.
  This reproduces that reasoning empirically rather than by projection, one level up, and is itself a finding
  the recommendation below leans on.
- **Judging-run shape:** `coverage.enabled: false` (Stryker measures its own per-test coverage),
  `testTimeout: 120_000`, one worker thread reused across files (`pool: 'threads'`,
  `poolOptions.threads.singleThread: true`) to avoid paying Vitest's cold start per mutant. Unlike
  `vitest.mutation.config.js`, this did **not** set `isolate: false`: that setting is safe for `src/core`
  specifically because it is provably pure (no module-level mutable state, no ambient clock or randomness —
  `eslint.config.js` forbids all four ways and `tests/unit/core/purity.test.js` proves it), and that guarantee
  does not extend to `src/game`, which owns the loop, input timestamps and session lifecycle. Leaving
  isolation on costs more wall clock and is the honest choice for a number meant to be read at face value.

and explicitly not what a quiet CI runner would show. This container ran a sibling agent's `src/core`

Fifteen minutes is *faster* than the core baseline's own 49m28s/27m36s figures despite mutating more (2189
against 1320) — this judging suite (552 tests) is nearly double `src/core`'s (286), but each of its tests is
apparently cheap enough, and the container was apparently kind enough at that particular quarter hour, that
the average mutant still only cost 34.20 test-runs against core's 18.84. That is not a claim that `src/game`
is somehow cheaper to mutate than `src/core` in general — a contended container's wall clock is exactly the
kind of number `perf-baseline.md` already warns swings by "a factor of two between runs of unchanged code".
Take the fifteen minutes as "this shape of run, on this contended box, today" and nothing more; the failed
`tests/sim` attempt above is the more durable finding.

## Recommendation: gate later, in two pieces, not as one number today

**Gate `src/game` eventually — but not as a single score, not yet, and never per-PR.**

**Why eventually, and why nightly only.** `loop.js` and `gameStateMachine.js` are two of the four systems
`AGENT-ROLES-AND-WORKFLOW §1` names architecture-critical, and this run found real, specific rules neither one
proves (survivors #1–5 above) — exactly the "test that is not testing" this sprint exists to surface. That
argues for the same discipline `src/core` gets. But `src/game` is not `src/core`: it owns real time, DOM
event listeners and injected browser hooks rather than pure functions of a seed, its dedicated suite is
already noticeably heavier (`tests/unit/game` + `tests/agent` alone was 552 tests against `src/core`'s 286),
and the `src/core` gate this run reused already has to fit AC2's twenty-minute CI budget with room to spare —
`src/game` would not fit inside what is left of it. A `src/game` gate belongs next to `test:perf:frametime` in
`nightly.yml`, never in `ci.yml`.

**Why two pieces, not one number.** This run's honest 72.22 % is not one thing:
- `src/game/loop.js`, `gameStateMachine.js`, `input.js`, `inputLatency.js`, `replayPlayer.js`,
  `testHooks.js`, `cpuPlayer.js` and `session.js` — everything judged fully and fairly by
  `tests/unit/game` + `tests/agent` — scored 71.68–100 % individually. These are ready for a real, if modest,
  threshold once a KI-17-02-shaped pass has triaged today's survivors (kill the real gaps, like #1–9 above;
  document any genuine equivalents). A first threshold of **70 %**, comfortably under what several of these
  files already clear and achievable for the rest without pinning implementation details, is a defensible
  starting number — raised the same way `src/core`'s will be, from an honest baseline upward, never invented.
- `src/game/bots/**` (`greedy.js`, `survivor.js`, `levels.js`, `policy.js`) **should not be gated from this
  run's numbers at all.** `levels.js`'s 23.08 % is demonstrated above to be substantially an artefact of the
  one run that could not include `tests/sim`, and `greedy.js`/`survivor.js` (65–67 % here) would very likely
  also move once judged by the suite that actually drives them through full matches. Setting a threshold from
  today's bots numbers would either lock in a number that flatters nothing or, worse, invite exactly the
  "narrow the code to kill a mutant" trap `QA-STRATEGY §9` warns against, aimed at survivors that a wider
  judging set might kill for free. The bots need re-measuring — with `tests/sim` restored, on a quieter
  container or with the hook timeout raised well past 90 s, ideally as its own longer-budget nightly slice —
  before any number attached to them means anything.

**In short:** the ten worst survivors above are real findings and worth acting on regardless of whether a
gate ever exists; the question this ticket actually asks — gate now, and at what number — is "not yet, and
not as one number," with a concrete path to both halves.
